No credentials or tokens were requested or used. These steps are yours:

1. **Create the repository** on GitHub (private or public, your choice).
2. **Add the remote** and push:

   ```bash

   git remote add origin https://github.com/<your-username>/<repo-name>.git
   ```

## C. What still needs deciding for cloud deployment

Each item is a real fork in the road. Recommendations are given, but the choice
is yours.

### C1. Frontend hosting

The build output is fully static (`frontend/dist/`), so almost anything works.

| Option | Fit | Notes |
| --- | --- | --- |
| **Vercel** | Recommended | Zero-config Vite support, free tier, instant previews per PR |
| Netlify | Good | Free tier, form handling if the contact page is ever wired up |
| GitHub Pages | Acceptable | Free, but SPA routing needs a `404.html` rewrite for deep links |
| Cloudflare Pages | Good | Free, fast, generous bandwidth |
| Any web server / nginx | Fine | Serve `dist/` as static files with a history fallback |

**Decision needed:** provider, and whether the built SPA is served from the same
host as the API.

### C2. Backend hosting

| Option | Fit | Notes |
| --- | --- | --- |
| **Render / Railway / Fly.io** | Recommended for a first deploy | Free or low-cost tiers, persistent env vars, easy Python support |
| A VM (DigitalOcean, Hetzner, AWS EC2) | Most control | You own the process supervisor, firewall, TLS and backups |
| AWS Lambda + API Gateway | Poor fit | Cold starts, awkward for a stateful SQLite file, container packaging needed |
| Heroku | Workable | Paid; the simplest UX if you want managed TLS and env vars |

**Decision needed:** provider, region, and whether it exposes plain HTTP behind
a proxy or terminates TLS itself.

### C3. Database hosting and persistence — **the biggest decision**

SQLite is a single local file, and this is the part that most often breaks on
first deploy.

| Option | Fit | Consequence |
| --- | --- | --- |
| **Ephemeral disk + a real database** | **Strongly recommended** | Migrate to PostgreSQL and use a managed instance (Supabase, Neon, RDS). Requires schema migration work, not a URL swap. |
| Persistent volume (e.g. a VM's disk, Fly volume) | Acceptable for a demo | Works, but backups, upgrades and multi-instance scaling remain your problem. |
| Ephemeral disk + SQLite | **Will lose data** | Most PaaS platforms wipe the filesystem on every deploy and restart. Every user, device and pickup record disappears. |

**Decision needed:** if you deploy to any platform with an ephemeral filesystem,
you **must** either mount a persistent volume or move to a client-server
database. Do not ship SQLite on ephemeral storage.

There is also **no migration tool** (Alembic is not present) and **no backup
routine**, so a persistent volume is a single point of failure.

### C4. ML model deployment

The trained pipeline is a file, loaded lazily once per process. Three
approaches:

| Approach | Fit |
| --- | --- |
| **Train once in CI / on a build machine, commit or upload the artifact** | Recommended. Keeps the running service free of training cost and keeps training reproducible. |
| **Train on the host at deploy time** | Works, but adds ~seconds of startup and needs the dataset present. |
| **Serve the model separately** | Explicitly out of scope for this project. |

Whichever you choose:

- The artifact is **git-ignored today**, so a `git clone` will not contain it.
  Either upload it to your host or run
  `python -m app.scripts.train_valuation_model` during your deploy.
- Set `SMARTCYCLE_DATA_DIR` (or `VALUATION_MODEL_PATH`) to wherever you place it.
- The app **degrades safely**: with no model present it falls back to the
  rule-based estimator and labels every result `rule_based`.
- The model is **cached in memory on first use**, so retraining requires an API
  restart.
- Reminder: the model is trained on **synthetic data** and is a demonstration
  artefact. Do not present its metrics as market accuracy.

### C5. Environment variables to set on the hosting platform

Backend — set these in your platform's dashboard, **not** in the repository:

| Variable | Example | Required |
| --- | --- | --- |
| `JWT_SECRET_KEY` | a 48+ byte random value | **Yes** |
| `CORS_ORIGIN_PRODUCTION` | `https://your-frontend.example.com` | Yes, in production |
| `DATABASE_PATH` | `/data/smartcycle.db` or omit if using a managed DB | Depends |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `60` | No |
| `SMARTCYCLE_DATA_DIR` | `/app/backend/data` | Only if the model lives elsewhere |
| `VALUATION_MODEL_PATH` | `/app/backend/data/valuation_model.joblib` | Only if overriding |

Frontend — set at **build** time, because the value is inlined into the bundle:

| Variable | Example |
| --- | --- |
| `VITE_API_URL` | `https://your-api.example.com` |

If you leave `VITE_API_URL` unset for a production build, the app calls the
**same origin** as the page. That is correct when one host serves both, and
wrong when they are split across two hosts.

### C6. CORS origin

Set `CORS_ORIGIN_PRODUCTION` to the exact deployed frontend origin, **with the
scheme** — `https://app.example.com`, not a bare host. The backend always keeps
its local development origins, so this cannot break local work, and a wildcard
is discarded with a warning because the API sends credentials.

Your frontend origin and this value must agree; if they do not, the browser
blocks every request and the backend log shows no matching
`Access-Control-Allow-Origin`.

### C7. Public URLs

Two values to settle, and they feed each other:

- **Public API URL** — where the FastAPI service will live, e.g.
  `https://api.example.com`. Becomes `VITE_API_URL` and must be allowed by CORS.
- **Public frontend URL** — where the built SPA will live, e.g.
  `https://app.example.com`. Becomes `CORS_ORIGIN_PRODUCTION`.

**Decision needed:** same host behind one reverse proxy (simplest — CORS becomes
a non-issue) or two hosts (needs CORS configured correctly and a rebuild after
changing `VITE_API_URL`).

### C8. HTTPS

**Required before any real use.** The app transmits passwords and bearer tokens;
over plain HTTP they are readable by anyone on the network. Use a platform that
terminates TLS for you (Vercel, Netlify, Render, Railway, Fly all do), or
Let's Encrypt via Caddy/nginx on a VM. Also enable HSTS and redirect HTTP to
HTTPS.

### C9. Custom domain (optional)

A cosmetic but real decision: register a domain, point a CNAME/ALIAS at the
frontend host and an A/CNAME at the API host, then update `VITE_API_URL`,
`CORS_ORIGIN_PRODUCTION` and rebuild the frontend. Defer this until the app
works on platform-provided URLs.

### C10. Also outstanding before a real launch

Ordered roughly by how much they matter:

1. Replace the `localStorage` token with `HttpOnly`, `Secure`, `SameSite`
   cookie sessions plus refresh-token rotation and server-side revocation.
2. Add rate limiting to login and registration.
3. Replace `init_db()` with Alembic migrations.
4. Paginate the admin list endpoints.
5. Add CI running `npm run build` and the backend test suite on every push.
6. Add structured logging, error tracking and uptime monitoring.
7. Only then, consider whether the synthetic valuation model should be replaced
   with real data — until then it must not be presented as market pricing.

## Local setup on any machine

For whoever clones this, and for your own deploy verification:

```bash
# backend
cd backend
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env      # fill in JWT_SECRET_KEY
python -m app.scripts.create_admin --email you@example.com --name "Your Name"
uvicorn app.main:app --reload --port 8000

# frontend, second terminal
cd frontend
npm install
npm run dev
```

Optional but recommended:

```bash
cd backend && python -m app.scripts.train_valuation_model   # enable ML valuation
cd backend && ADMIN_EMAIL=... ADMIN_PASSWORD=... python -m app.scripts.run_api_tests --unit
```

The application runs fully without the trained model; valuations simply fall
back to the rule-based estimator and are labelled as such.
