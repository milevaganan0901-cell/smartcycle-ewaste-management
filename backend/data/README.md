# Valuation dataset — provenance and audit

> **The dataset used to train the SmartCycle valuation model is SYNTHETIC.**
> It was generated by this project. It is **not** real market data, was **not**
> collected from users, and was **not** scraped from any marketplace.
>
> **The current valuation model is a development/demo model trained on synthetic
> data and should not be interpreted as a production market-pricing model.**

Audited in Stage 4B. Every figure below was measured, not estimated.

---

| Property | Value |

## 2. How the target was produced

`estimated_purchase_value` was computed with the project's **own documented
rule-based formula** (`app/services/valuation.py`) and then multiplied by a
uniform noise factor in `[0.93, 1.07]`, with a floor applied afterwards:

```
reference = original_purchase_price (when > 0) else the category reference value
value     = reference
           × max(0.25, 0.88 ** age)
           × condition factor
           × working-status factor
           × physical-damage factor
value     = max(500, value × noise)
```

Stage 4B re-derived this from the CSV and confirmed **372 of 420 rows (88.6%)**
sit inside the expected `[0.93, 1.07]` noise band once the floor is accounted
for. The remaining rows are floor-clipped, which inflates the apparent ratio
against the *unclipped* formula — expected, not an anomaly.

### The single most important consequence

**The dataset's target was generated from the rule-based estimator.** That makes
the rule-based estimator an unusually strong baseline *on this data* — close to
ground truth rather than merely similar to it. This is measured and reported in
Stage 4B rather than hidden; see the baseline table in
[`STAGE_4B.md`](../../docs/STAGE_4B.md).

## 3. Measured data-quality audit

All measured on the committed file.

### Missing values

| Column | Missing | Share |
| --- | --- | --- |
| `original_purchase_price` | 63 | 15.0% |
| all six other columns | 0 | 0% |

The missing price is deliberate and realistic: the field is optional in the
Sell Device form, and the training pipeline imputes it (median for numeric,
most-frequent for categorical) rather than assuming it is present.

### Duplicates

| Check | Result |
| --- | --- |
| Duplicate feature tuples (excluding target) | **0** — 420/420 unique |
| Fully identical rows | **0** |

Real-world datasets essentially always contain duplicates. Zero duplicates is
itself a sign of synthetic generation, and is recorded here as such rather than
presented as a quality win.

### Impossible or suspicious values

| Check | Result |
| --- | --- |
| Negative ages | 0 (range 0–9, mean 4.36) |
| Non-positive purchase prices | 0 (range ₹600 – ₹236,500, mean ₹47,024) |
| Negative or zero targets | 0 (range ₹500 – ₹71,724, mean ₹9,695) |
| **Targets exactly on the ₹500 floor** | **53 (12.6%)** |

The ₹500 floor is a genuine modelling constraint, not a defect. Those 53 rows
share one identical target, so **no regression model can separate them** — they
contribute irreducible error and put a ceiling on the achievable fit. The
training run reports this in `metrics_ceiling_note`.

### Category distributions

| Column | Distinct | Distribution |
| --- | --- | --- |
| `device_category` | 9 | 9.0% – 12.9% (near-uniform) |
| `brand` | 26 | 1.2% – 9.5%, smooth taper |
| `condition` | 5 | 18.3% – 24.0% (near-uniform) |
| `working_status` | 3 | 29.3% – 38.1% |
| `physical_damage` | 3 | 32.9% – 34.0% (near-uniform) |

**These distributions are implausibly balanced.** Real survey or transaction
data is never within a few points of uniform across condition grades. The
near-uniform spread is direct evidence of uniform random sampling during
generation, and is a further reason the model must not be read as
market-accurate.

Brands are internally consistent with their categories (a Laptop never carries
a printer brand), so the generator was at least coherent.

## 4. Leakage review

Checked for Stage 4B:

- **No target leakage.** The target is derived only from the seven features plus
  the reference value. No feature is computed from the target.
- **The ratio target cancels the reference deliberately.** The model predicts
  `value / reference`, and `reference` is reconstructed at prediction time from
  the same inputs. The reference is never a model input, so the model cannot
  shortcut the arithmetic.
- **`original_purchase_price` is a legitimate feature, not leakage.** It is
  available at prediction time and is genuinely predictive; it is not derived
  from the label.
- **Train/test separation is clean.** `train_test_split` is applied before
  fitting, and model selection used cross-validation over the full set with the
  held-out split reserved for the final unbiased estimate.

## 5. Search for a public dataset (Stage 4B, best effort)

A genuine search was performed. Public candidates **were** found, downloaded,
and inspected. They were **rejected for specific, stated reasons**.

### What was checked

| Source | Result |
| --- | --- |
| UCI ML Repository API — `e-waste`, `electronic waste`, `used device`, `resale`, `laptop`, `hardware price` | **0 results** each. The only `smartphone` hits are Human Activity Recognition datasets, unrelated to pricing. |
| Kaggle — `mariyamalshatta/recell-used-devices-prices` | Downloaded and inspected. Licence **CC0: Public Domain**, 3,454 rows, 15 columns. |
| Kaggle — `ahsan81/used-handheld-device-data` | Downloaded and inspected. Licence **CC0: Public Domain**, 3,454 rows. Verified to be the **same 3,454 records** as the previous file (100% numerical agreement), differing only in column names and float formatting — so this is one dataset, not two. |

### Why the candidate was rejected

| Requirement | Candidate |
| --- | --- |
| `device_category` | **absent** — no category column; rows are phones/tablets only |
| `brand` | present (`brand_name`) |
| `age` | proxy only (`release_year` + `days_used`, not the app's "age in years") |
| `condition` | **absent** |
| `working_status` | **absent** |
| `physical_damage` | **absent** |
| `original_purchase_price` | **absent** (only `normalized_new_price`, an uncalibrated proxy) |

Five of seven features are missing outright, including **`working_status` and
`condition`, which together account for roughly 68% of the fitted model's
feature importance**. Two further blockers:

1. **The target is a unitless normalised price** (`normalized_used_price`, range
   ≈ 1.54 – 6.62) with no currency, region or calibration. The application
   stores and displays **rupees**. Converting a normalised score into an INR
   figure would mean inventing a rate, which would be fabrication.
2. **Category coverage is 2 of the application's 9** — phones and tablets only.
   A model trained on it could not value a laptop, monitor, television, printer,
   desktop, accessory or "other electronics" submission at all.

Adopting it would have meant discarding the features the valuation actually
depends on, inventing a currency conversion, and being unable to value most of
the devices the app accepts. Forcing it in purely to look more advanced would
have made the system **less** honest, not more.

**Decision: keep the synthetic dataset**, labelled as synthetic everywhere it is
referenced.

## 6. What would be needed for a real model

1. A lawfully obtained dataset of **actual transaction prices**, in **rupees**,
   covering **all nine device categories**.
2. Recorded **condition and working-status** at the point of sale, not inferred.
3. Enough rows for the categories that are naturally rare — a few hundred rows
   cannot support nine categories plus 26 brands without the model falling back
   to category averages.
4. An honest re-run of this same evaluation, where the rule-based baseline is
   **no longer** the data-generating process. Only then would a model-vs-rules
   comparison mean anything.

Until then the correct statement is the one at the top of this file.

## 7. Regenerating and retraining

Training is a **manual, separate** step and never runs on a device submission
or at server start:

```bash
cd backend
python -m app.scripts.train_valuation_model
```

Optional flags: `--dataset <path>` and `--model-out <path>`.

The run prints the model comparison, the held-out metrics, both baselines, and
an explicit statement when the ML model does not beat the rule-based estimator.
It writes `valuation_model.joblib` and `valuation_model_metrics.json`. Restart
the API afterwards — the pipeline is cached on first use.

The **dataset** is not regenerated by the training script; it is a committed
file. The original generator used `random.Random(20260926)`, so the CSV can be
reproduced byte-for-byte if needed.
